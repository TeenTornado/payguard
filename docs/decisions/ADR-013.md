# ADR-013: Retrieval is scoped ONLY to grounding the analyzer

**Status:** Accepted
**Date:** 2026-08-24

## Context

Retrieval-augmented context is useful in exactly one place in PayGuard: helping the LLM analyzer
judge code against known Razorpay rules and labeled precedents. It is tempting to reuse the
retriever elsewhere — to influence static rules, to pick verification scenarios, to score
exposure, or to let the verifier consult "similar cases." Each of those would blur the
system's guarantees.

## Decision

The retriever grounds the **analyzer prompt** and nothing else. Specifically:

- Static detection (ADR-002 deterministic checks), the verifier (ADR-001 sole arbiter), exposure
  scoring, and remediation do NOT consult the retriever.
- Grounding is opt-in via `PAYGUARD_ANALYZER=grounded` (default off), so the baseline analyzer is
  unchanged and the two are directly comparable.
- Retrieved references are **non-authoritative context** injected in a clearly-separated
  `<<<REFERENCE>>>` block; the code stays the only thing under analysis, and repo content is still
  treated as untrusted data, never instructions (the injection boundary is unchanged).
- The analyzer's output schema is unchanged and enum-validated; a VERIFIED verdict and any
  MEASURED amount still come only from the verifier.

## Consequences

- Grounding can change which hypotheses the LLM proposes, but cannot change what gets VERIFIED or
  what MEASURED amount is written — the money-safety guarantees are untouched.
- The retriever is a self-contained, testable component with a single caller.
- If grounding does not beat the baseline on the frozen splits, it stays behind the flag and the
  rest of the system is unaffected (see docs/evaluation.md for the measured verdict).
